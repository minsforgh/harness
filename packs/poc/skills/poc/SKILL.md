# poc

기획 문서가 정한 질문에 답하는 짧은 POC를 진행한다. 기간 제한은 두지 않고 "그 질문에 답할 수 있는 최소 범위"를 지킨다. 지킬 것(범위, 튜닝 값, 폴더, 느슨한 확인)은 묶음 규칙(harness-poc `rules.md`, 세션마다 주입)에 있고, 이 스킬은 단계 순서와 단계마다 만들 것만 다룬다.

POC의 목적은 메카닉과 재미를 확인하는 것이고 개발은 수단이다. 만들면서도 기획 쪽 생각을 놓지 않는다: 이 장르에서 이 메카닉이 어떻게 읽히는지, 유사작과의 차이가 실제로 느껴지는지, 만들어 보니 무엇이 비싸고 무엇이 쌌는지. 아이디어 탐구와 기획 문서 쓰기는 범위 밖이다. 기획 문서의 내용(컨셉, 설계 생각, 범위, 규칙, 보고 싶은 신호)을 다시 정하지 않고, 이 프로젝트에서 어떻게 만들지(기술 전제, 작업 단위, 마일스톤)를 정한다.

## 경로

- dev-wiki: `claude plugin marketplace list --json`의 `harness` 항목 `path`(`<dev-wiki>/_harness`)의 부모 폴더
- 기획 문서: 사용자가 준 경로. 없으면 `<아이디어 폴더>/목록.md`에서 장소가 이 프로젝트인 줄의 `<아이디어 폴더>/<IdeaId>/기획.md`
- 설계 방법론: 이 스킬 폴더의 `design-methods.md`. P1의 첫 마일스톤 고르기, P4, P5를 시작할 때 그 절만 읽는다

## 이어 하기

시작할 때 상태를 보고 비어 있는 첫 단계부터 한다. 끝난 단계를 다시 묻지 않는다.

| 상태 | 시작 |
|---|---|
| `docs/archive/idea.md`가 없다 | P1. 기획 문서가 없고 아이디어만 있으면 사용자와 기획 문서(주 질문, 범위, 보고 싶은 신호)부터 정리한다. 정할 것이 많으면 grilling을 제안한다 |
| `docs/overview.md`가 `상태: 승인 전` | P2 |
| "값" 표 PocId가 비었거나 `Assets/<PocId>/`가 없다 | P3 |
| 그 밖 | `docs/tasks.md`의 남은 일부터 P4. 사용자가 플레이테스트나 마감을 말하면 P5, P6 |

## P1 기획 문서 받고 나누기

1. 기획 문서를 읽는다. 확인한다: `status`가 확정이나 넘김인가, 설계 생각(2절), POC가 확인할 것(3절), 보고 싶은 신호(9절)가 채워져 있는가. 빠진 칸만 사용자에게 묻는다. 3절이 비었으면 나누기 전에 그 질문부터 사용자와 정한다(나머지가 그 위에 선다).
2. 읽으며 드는 기획 쪽 생각(설계 생각과 다르게 보이는 점, 빠진 관점)은 짧게 말한다. 고칠지는 사용자가 정한다.
3. 기획 문서를 그대로 `docs/archive/idea.md`로 복사한다. 넘길 때의 사진이고 고치지 않는다.
4. 절마다 자리로 옮긴다. 확정과 거절한 방향은 문장을 바꾸지 않는다. 범위를 바꿔야 할 것 같으면(볼륨, 만들지 않는 것) 옮기면서 고치지 말고 먼저 말한다.

   | 기획 문서 | 자리 |
   |---|---|
   | 1 피치 | 개요 "한 줄", `docs/game.md` "피치" |
   | 3 POC가 확인할 것 | 개요 "주 질문", "가장 불확실한 가정" |
   | 5 범위 | 개요 "목표", "범위", "완료 기준" |
   | 9 보고 싶은 신호 | 개요 "보고 싶은 신호" |
   | 10 미정 | 개요 "미정" |
   | 2 설계 생각, 4 확정과 거절한 방향, 6 루프, 11 확장 후보, 유사작 | `docs/game.md` |
   | 7 규칙 | 시스템마다 `docs/systems/<system>.md`(`_template.md`를 복사). 조작은 Input Actions의 액션 이름으로 옮긴다. 작은 시스템 하나면 개요에 같이 써도 된다 |
   | 8 튜닝 초기값 | 옮기지 않는다. P4 첫 작업에서 TuningConfig 초기값으로 넣고, 그때까지는 `docs/archive/idea.md`가 원본이다 |
   | 12 넘기기 | 옮기지 않는다(장소는 `<아이디어 폴더>/목록.md`가 맡는다) |

5. `docs/tasks.md`를 만든다: 마일스톤(M1 가장 불확실한 가정 확인, M2 한 판이 처음부터 끝까지 이어짐, M3 플레이테스트와 튜닝)과 그 아래 작업 단위(`- [ ]`). 첫 마일스톤은 `design-methods.md` P4 표로 고르고, 기획 2절 재미 줄의 "첫 판의 목표와 대가"를 M1에 넣는다. Unity 빌드보다 싼 방법으로 답이 나오는 질문(수치 균형, 지배 전략 여부)이면 그 방법(시트, 계산 스크립트, 규칙 확인 화면)을 첫 작업으로 둔다. 병렬로 나눌 수 있는 작업에는 "병렬 가능: 이유"를 붙인다.
6. 기술 전제(입력 액션 맵, UI 방식, 바꿀 전역 설정)는 `AGENTS.md` "이 프로젝트의 규칙"에 쓴다. 한 줄 소개를 채우고, "먼저 읽을 것"에 `docs/game.md`(게임 설계)를 더한다.

## P2 승인

구현 전 유일한 승인 지점이다. 승인된 범위 안의 작업은 다시 승인받지 않는다.

1. 주 질문, 가장 불확실한 가정, 범위, 보고 싶은 신호, 시스템 목록, M1 작업을 짧게 요약해 보이고 문서 경로를 알린다. 수정 요청은 반영해 다시 보인다.
2. 승인되면 개요를 `상태: 진행 중`으로 바꾸고 `docs(<PocId>): POC 문서` 하나로 커밋한다.
3. dev-wiki 쪽: `<아이디어 폴더>/<IdeaId>/` 폴더를 지우고 `<아이디어 폴더>/목록.md`의 그 줄 장소를 이 프로젝트 경로로 맞춘다. 원본은 프로젝트(`docs/archive/idea.md`)에 있다. dev-wiki는 커밋하지 않고 사용자에게 알린다.

## P3 폴더

1. 에디터가 열려 있어야 한다. `unity status`로 보고, 없으면 `unity open <프로젝트>`로 연다(처음 열 때 Library를 만드느라 몇 분 걸린다).
2. "값" 표 PocId를 채운다(영문 PascalCase, 기획 문서의 IdeaId와 같게).
3. `harness-unity:unity-module`(그 스킬 표의 POC 줄)로 `Assets/<PocId>/`(asmdef `<PocId>`, 쓰는 패키지만 참조. `Unity.InputSystem` 등), `Scripts/Editor/`의 Editor asmdef `<PocId>.Editor`, `Input/<PocId>.inputactions`를 만든다. 입력 에셋은 `Assets/Settings/InputSystem_Actions.inputactions`를 복사해 시작하면 빠르다(원본은 그대로 둔다). 처음 하위 폴더는 묶음 규칙대로다.
4. 확인 씬 `Assets/<PocId>/Scenes/<이름>.unity`를 만들고 빌드 씬 목록의 `SampleScene`을 이 씬으로 바꾼다. "값" 표의 확인 씬과 확인 명령(묶음 규칙 "끝낼 때 확인")을 채운다.
5. 처음 열며 에디터가 남긴 변경(`Packages/packages-lock.json`, 설정 파일 등)은 따로 `chore: 에디터가 처음 열며 바꾼 설정` 커밋으로 넣고, 이 단계는 `chore(<PocId>): POC 폴더와 확인 씬`으로 커밋한다.
6. 보고: 만든 폴더와 파일, 다음 단계(P4 첫 작업).

## P4 구현

1. `design-methods.md` P4 절을 읽고 `docs/tasks.md` 순서대로 한다. 첫 작업은 공통 기반(TuningConfig, 데이터 ScriptableObject, `docs/archive/idea.md` 8절의 초기값)이다.
2. 씬, prefab, 조작감, 연출, 작업 사이 통합은 직접 한다. 나눠 맡기는 것은 core 규칙(같은 시스템을 두 곳에서 동시에 고치지 않는다) 안에서 이득이 분명할 때만이고, 오케스트레이션은 harness-orca 묶음을 켰을 때만 쓴다.
3. M1에서 가장 불확실한 가정이 틀렸으면 다음 작업으로 넘어가지 않고 사용자에게 알린다.
4. 작업 단위가 끝나면 묶음 규칙 "끝낼 때 확인"과 "플레이 확인"대로 하고 커밋한다(core 커밋 방식).
5. 마일스톤이 끝나면 시스템 문서를 지금 동작에 맞추고, 사용자에게 플레이테스트(P5)를 할지 묻는다.

## P5 플레이테스트

1. `design-methods.md` P5 절을 읽는다. 다른 사람에게 시킨다면 그 진행 방법을 짧게 안내한다.
2. 사용자가 개요의 완료 기준과 보고 싶은 신호를 보며 플레이하고 피드백을 준다. 재미 판정은 사용자가 한다.
3. 피드백을 기획 관점으로 다시 읽어 사용자와 이야기한다: 설명 없이 이해했는가(명료성), 유사작과 다르게 느꼈는가(독창성), 선택을 고민했는가(깊이), 주 재미의 신호가 보였는가(재미). 무엇이 문제였는지에 따라 고칠 곳이 갈린다.
4. 고칠 때는 먼저 TuningConfig 수치로 풀 수 있는지 본다. 수치로 안 되면 조작이나 규칙 변경안을 짧게 내고 고른 것만 반영한다. 표현(색, 피드백, 연출)이 규칙을 읽히게 하는 문제면 그쪽 안도 낸다.
5. `docs/playtest.md` 끝에 `## YYYY-MM-DD 플레이테스트`로 적는다(형식은 그 파일 머리). 결론은 계속, 피벗, 중단 중 하나다. 멈출 신호가 나오면 튜닝을 이어 가지 않고 알린다.

## P6 마감

1. 시스템 문서와 `docs/game.md`를 지금 상태에 맞춘다.
2. 사용자와 설계 회고를 `docs/playtest.md` 끝 `## YYYY-MM-DD 설계 회고`로 쓴다. 기획 문서(`docs/archive/idea.md`)의 설계 생각과 비교해 맞은 것과 틀린 것을 적는다.
3. 개요의 상태를 고른 결과로 바꾸고 커밋한다.
   - **보류**: 그대로 둔다.
   - **보관**: 태그 `poc/<PocId>`를 남긴다. 사용자가 승인하면 `unity projects clean <프로젝트>`로 Library 같은 다시 만들 수 있는 폴더를 지운다. 프로젝트 폴더는 지우지 않는다.
   - **선정**: 이 프로젝트를 그대로 키운다. `node <dev-wiki>/_harness/apply.mjs <프로젝트> --profile unity-game`으로 다시 적용하고(문서 수준 standard), `claude plugin disable harness-poc@harness --scope project`로 poc 묶음을 끈다(느슨한 확인도 같이 끝난다). "값" 표의 PocId 행은 지워도 된다. 여럿이 만들면 팀 구성으로 간다.
4. `<아이디어 폴더>/목록.md`의 그 줄 상태: 보관이나 보류면 "접음"으로 하고 설계 회고에서 가장 중요한 배움을 한 줄로 적는다. 다음 아이디어 탐구가 이 기록을 참고한다.
5. 위키 환류(프로젝트 허브, 다음 프로젝트에도 쓸 배움)는 dev-wiki 세션의 `project-wrapup`이 한다고 알린다.

## Gotchas

- asmdef를 두면 패키지 어셈블리를 자동으로 보지 못한다. `Unity.InputSystem` 등을 참조에 넣지 않으면 컴파일 에러가 난다.
- 세션 폴더를 옮기면 앱이 이전 작업 폴더의 파일을 새 폴더 루트로 복사할 수 있다. 내가 만들지 않은 파일은 지우지 말고 사용자에게 알린다.
- 기획 문서의 튜닝 표를 시스템 문서에 옮겨 적지 않는다. 데이터와 두 곳이 되어 어긋난다.
