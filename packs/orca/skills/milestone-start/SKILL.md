# milestone-start (harness-orca)

칸이 없는 항목은 그날 생각나지 않으면 빠졌다(AoGD의 화면 확인, 콘텐츠 품질, 한도 대응). 그래서 답할 질문과 판정을 고정하고, 기계 판정이 통과해야 시작한다. 목표, 범위, 완료 장면, 확인 명령, 문서 수준처럼 모든 프로젝트에 필요한 것은 core 문서가 맡고, 여기서는 오케스트레이션에만 필요한 것을 정한다. 마일스톤마다 다시 쓰는 절차라 프로젝트 한 번의 "킥오프"가 아니라 마일스톤 시작으로 부른다. `<이 폴더>`는 이 스킬의 폴더다.

## 규칙

- 여러 턴에 걸친다. 시작할 때 세션 effort가 high보다 낮으면 올리자고 한 줄로 권한다(스킬의 effort는 첫 턴에만 걸린다).
- 질문은 단계마다 묶어 한 번에 묻고 추천 답을 같이 낸다. 답할 수 없거나 해당 없으면 칸에 "생략: <이유>"를 쓴다. 비워 두지 않는다.
- 승인은 두 번 받는다: K2 계약 뒤, K5에서 기준과 대기열과 점검 결과를 함께.
- 단계가 끝날 때마다 파일에 쓴다. 세션이 끊기면 파일에서 이어 간다(비어 있는 첫 단계부터).
- 절차 자체의 고칠 점은 보고에 적는다(원본은 dev-wiki `_harness/`에서 고친다).

## 단계

0. **준비**: `AGENTS.md` "값" 표에 `worker 구현` 행이 있는지 본다. 없으면 harness-orca가 꺼진 것이다. `harness-user:harness-apply`로 지금 켜진 묶음에 orca를 더해 적용한다(`--packs <켜진 묶음>,orca`).
1. **K1 개요**: `docs/overview.md`의 한 줄, 목표, 범위(하지 않는 것, 규모), 완료 기준(완료 장면)이 채워졌는지 본다. 비었으면 먼저 채운다. 비교할 이전 프로젝트가 있으면 규모를 그 수치로 적는다.
2. **K2 계약**: "값" 표의 오케스트레이션 행을 채운다. 함께 "값" 표의 확인 명령이 머지 기준으로 충분한지, 화면을 무엇으로 확인하는지(켜진 묶음 규칙, Unity는 캡처와 렌더 단언)를 확인한다. 다음 마일스톤에서는 바뀐 행만 다시 묻는다(계정, 모델, 한도는 바뀐다).

   | 행 | 묻는 것 | 추천 |
   |---|---|---|
   | coordinator | 계획과 판단, 실행 루프 각각의 모델과 effort | 계획과 판단은 가장 좋은 모델 high, 실행 루프는 한 단계 낮은 모델. deskpet과 AoGD는 실행 루프까지 비싼 모델로 돌아 비용이 가장 컸다 |
   | worker 구현, 잡무, 리뷰 | `agent:model:effort` 후보를 앞부터 `>`로. model을 비우면 그 agent의 기본값 | 지금 쓸 수 있는 계정과 한도를 보고 정한다. 리뷰는 구현과 다른 worker. R 기준이 없으면 리뷰는 "생략: R 기준 없음" |
   | 병렬 상한 | 동시 worker 수 | 3. 메모리와 한도로 줄인다 |
   | 한도 기준 | `codex 85/95, claude 85` 형식(5시간/주간 %). 적지 않은 agent는 한도로 거르지 않는다 | 이 값(deskpet M14: 오래 도는 task 하나가 남은 한도를 다 쓰지 않게 여유를 둔다) |
   | 사람 승인 지점 | 승인 전에 시작하지 않는 것 | 설계 고정, 기준 이미지, 마일스톤 끝 사람 확인 |
   | 자동 머지 조건 | 사람 없이 머지하는 조건과 사람이 꼭 볼 것 | 확인 명령과 화면 단언 통과, 수정 금지 안 건드림. 사람은 H 기준과 확인 필요 영역 |
   | 수정 금지 | worker가 건드리면 안 되는 경로와 확인 필요 영역 | 설정, 패키지 목록, 이 저장소의 규칙 문서 |
   | 산출물 내용 검사 | 글, 아트처럼 형식 검사로 못 보는 내용을 누가 무엇으로 보나 | 사실 메모와 대조하는 리뷰 worker. 없으면 "없음" |

   여기서 승인 1을 받는다.
3. **K3 마일스톤 폴더**: `docs/changes/<YYYY-MM-DD>-<slug>/`를 만든다(`docs/changes/`가 없으면 만든다. 문서 수준 light도 같다). 안에 셋을 쓴다.
   - `proposal.md`: `<이 폴더>/milestone.md`를 복사해 채운다. 완료 기준 표는 `| C1 | 관찰 가능한 문장 | A/R/H |`다. 화면에 그려진 것을 보는 A나 R 기준을 하나 이상 둔다. 지난 마일스톤에서 사람이 찾은 결함 유형은 이번 단언으로 넣는다(lanternkeep: 단언한 유형은 사람 확인에서 다시 나오지 않았다).
   - `tasks.md`: 할 일 `- [ ]`.
   - `queue.json`: 대기열. role은 "값" 표의 `worker <역할>` 행이다. 같은 경로나 같은 시스템을 건드리는 task는 deps로 순서를 정한다. scope에는 고칠 코드와 함께 그 시스템의 문서(`docs/systems/<system>.md`)를 넣는다. 처음에 동시에 시작할 수 있는 task가 병렬 상한만큼 되게 쪼갠다(파일 경계가 겹치면 그것을 나누는 구조 task를 먼저).
     ```json
     { "milestone": "M1", "tasks": [
       { "id": "m1-core", "title": "...", "role": "구현", "deps": [], "scope": ["src/core/", "docs/systems/core.md"],
         "done": "측정 가능한 조건", "verify": "명령", "forbid": "건드리면 안 되는 것", "criteria": ["C1"] } ] }
     ```
4. **K4 사전 점검**: 아래를 실제로 돌리고 마일스톤 폴더의 `preflight.log`에 항목마다 한 줄씩 `PASS <키>`, `FAIL <키> <이유>`, `SKIP <키> <이유>`로 쓴다. 키가 하나라도 빠지면 판정이 막는다. 다음 마일스톤에서 바뀌지 않은 항목은 `SKIP <키> 지난 마일스톤과 같음`으로 쓴다(`trial`은 생략하지 않는다).
   - `orca`: `orca status --json` 성공(CLI 이름은 공식 스킬의 규칙대로 정한다)
   - `check`: "값" 표의 확인 명령이 지금 상태에서 기대 종료 코드로 끝남. 테스트가 0개일 때 실패로 보는지(Unity `-runTests`는 0개여도 0으로 끝났다)
   - `base`: worker worktree에서 기준 커밋이 보임. Orca 새 worktree는 원격 기준 브랜치에서 만들어져 push하지 않은 커밋이 안 보였다. push하거나 `--base-branch`를 준다
   - `clean`: 새 worktree에서 setup과 첫 임포트 뒤 `git status`가 깨끗함(에디터에서만 하고 저장하지 않은 설정은 새 worktree에서 다시 돌았다)
   - `tools`: worker 도구 버전과 업데이트 안내 꺼짐(Codex `check_for_update_on_startup = false`)
   - `codex-rules`: Codex worker가 `<orchestrate 폴더>/rule-files.mjs`가 낸 규칙 파일을 읽을 수 있음. Codex worker가 없으면 `SKIP codex-rules Codex worker 없음`
   - `trial`: "값" 표 worker 행의 첫 후보(서로 다른 `agent:model`마다)로 작은 시험 task를 보내 worker_done까지 받음. 값 표가 지금 계정과 모델로 도는지 마일스톤마다 이것으로 본다
   - `parallel`: 켜진 묶음 규칙의 병렬 항목(Unity는 그 규칙의 "병렬로 돌릴 때"). 해당 규칙이 없으면 `SKIP parallel <이유>`

   lanternkeep에서는 이 점검이 시작 전에 문제 다섯 개를 잡았다.
5. **K5 승인**: `node <이 폴더>/milestone-check.mjs <저장소> --pre-approval [--milestone <폴더>]`를 돌린다. 오류 0이면 결과와 알림을 보여 주고 승인을 받아, proposal "승인" 줄에 날짜를 쓴다. 날짜를 쓴 뒤 `--pre-approval` 없이 다시 돌려 오류 0을 확인하고 orchestrate로 시작한다. 오류가 있으면 시작하지 않는다.

다음 마일스톤은 K2(바뀐 행만), K3(새 폴더), K4, K5 순서로 한다.
