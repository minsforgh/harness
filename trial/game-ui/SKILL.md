# game-ui

상태: 시험 중. 쓸 때마다 아래 "시험 기록"에 한 줄 남긴다. 몇 번 써 보고 고친 뒤 시험을 끝낸다.

에이전트가 만든 UI가 어색한 이유는 셋이다: 화면을 보지 않고 좌표를 넣는다, 취향의 기준(레퍼런스, 디자인 값)이 없어 평균으로 만든다, 만든 결과를 시안과 비교하지 않는다. 이 스킬은 시안을 먼저 승인받고, 같은 변수 이름으로 옮기고, 캡처로 맞춘다.

## 프로젝트 값

| 무엇 | 위치 |
|---|---|
| 값 문서(분위기, 레퍼런스, 디자인 값, 부품 규칙) | AGENTS.md "작업 흐름 값"의 "UI 값" 칸. 없으면 POC는 `docs/UI.md` |
| 팔레트(게임이 쓰는 디자인 값) | 기본 부품 prefab 폴더와 TMP Style Sheet (위치는 값 문서에 적는다) |
| 고른 시안 | 값 문서와 같은 폴더의 `UI 시안/` |

값 문서가 없으면 `templates/UI.md`를 복사해 만든다. 기본 부품이 없으면 `templates/parts.md`대로 부품 prefab과 TMP Style Sheet를 만든다. 값 문서의 디자인 값 표와 시안 HTML의 CSS 변수, TMP 스타일 이름은 같은 이름을 쓴다(`--font-small` -> `small`). 값을 바꾸면 값 문서, 부품 prefab, 스타일을 함께 바꾼다(원본은 값 문서).

## 순서

1. 값 문서를 읽는다. "분위기"와 "레퍼런스"가 비어 있으면 2번부터, 차 있으면 3번부터 한다.
2. 레퍼런스: 장르와 분위기에 맞는 게임 UI를 WebSearch로 찾아 후보 4~6개를 링크와 한 줄 이유로 보여 주고 사용자가 고른다. 고른 것만 값 문서에 "무엇을 가져올지" 한 줄과 함께 적는다. 사용자가 이미지를 주면 그것도 적는다. 디자인 값이 비어 있으면 고른 레퍼런스에서 뽑아 제안하고 승인받는다.
3. 시안: `templates/mock.html`을 바탕으로 시안 2~3개를 만든다. 서로 다른 배치나 강조를 시도한다(색만 바꾼 시안은 하나로 친다). 실제 게임 캡처가 있으면 배경에 깐다(unity CLI `capture game_view`). 시안 전부를 비공개 페이지 하나(Artifact)에 나란히 보여 준다. frontend-design 스킬이 있으면 시안의 분위기(글꼴 느낌, 색 조합, 강조)를 잡는 데만 쓰고, uGUI로 옮길 수 없는 표현(앵커나 Layout Group으로 바꿀 수 없는 grid 배치, 스프라이트로 만들 수 없는 효과, 프로젝트 TMP 글꼴이 아닌 웹 글꼴)은 쓰지 않는다. `mock.html` 주석의 uGUI 제약이 우선이다. 글자는 game-text 규칙으로 쓰고, 정해지지 않은 문구는 그렇다고 표시한다.
4. 승인: 사용자가 고르거나 고칠 점을 말한다. 고친 시안을 다시 보여 주고, 확정된 시안의 HTML을 `UI 시안/<화면 이름>.html`로 저장한다.
5. 구조: 구현 전에 어디에 붙는지 정한다. 시험 중: 구조 단계와 uGUI 구현(6번)은 MaxwellDemon 한 곳에서만 확인했다. 새 프로젝트에 처음 쓸 때 컴파일, Boot 플레이, 씬 바로 플레이, 16:9가 아닌 창의 레터박스를 확인하고 아래 "시험 기록"에 남긴다. 프로젝트 `AGENTS.md`에 참조와 UI 구조 규칙이 있으면 그것이 우선이다.
   - HUD는 `SceneRoot` prefab의 HudCanvas 아래 nested prefab으로 둔다. 한 씬에만 쓰는 HUD도 그 씬의 HudCanvas 아래에 둔다. 화면 UI Canvas를 새로 만들지 않는다.
   - 화면은 모델을 읽기 인터페이스로만 본다. `ISceneBound.Bind(context)`에서 받고, 연속 값은 Update에서 읽고, 사건은 그 인터페이스의 event로 받는다. 화면이 모델 값을 바꾸지 않는다.
   - 화면 비율은 허용 비율 레터박스 안이다. 시안의 1920x1080이 띠 안쪽 영역이다.
6. 구현: uGUI와 TextMeshPro로 만든다. `unity:ui-ugui` 스킬을 따른다.
   - 화면은 기본 부품 prefab(패널, 글자, 막대, 구분선)의 prefab variant로 만든다. 부품에 없는 모양이 필요하면 부품을 먼저 더한다.
   - 배치는 RectTransform 앵커와 Layout Group으로 한다. 앵커 없이 좌표만 넣지 않는다. 안전 여백은 앵커에서 잰다.
   - 색은 기본 부품과 값 문서의 값만 쓴다. 글자 크기는 TMP Style Sheet의 단계로만 정하고 글자마다 크기를 넣지 않는다.
   - 대상 머리 위 표시처럼 월드에 붙는 것도 uGUI(World Space Canvas)로 만든다. 이것은 HudCanvas 밖에 있어도 된다.
   - 글자는 문자열 표의 키로 넣는다(game-text). 코드나 prefab에 문구를 직접 쓰지 않는다.
   - 코드는 내용(글자, 채움 비율, 켜고 끄기, 부품 상태)만 바꾼다. UI 오브젝트를 코드로 만들지 않는다.
7. 캡처 비교: 플레이 모드에서 게임 화면을 캡처해 확정 시안과 비교한다. 위치, 크기 비율, 색, 글자 크기가 눈에 띄게 다르면 고치고 다시 캡처한다. 최대 3번. 그 뒤 시안과 캡처를 나란히 보여 주고 사용자의 승인을 받는다. 3번 안에 못 맞춘 차이는 그대로 적어 보고한다.
8. 시험 기록을 한 줄 남긴다.

## 부품 기본 규칙

값 문서의 "부품 규칙"이 우선이다. 비어 있으면 이것을 쓴다.

- 화면 가장자리에서 안전 여백(기본 32px, 1920x1080 기준) 안에 둔다. 모서리에 붙는 부품은 그 모서리에 앵커를 둔다.
- 플레이 중 HUD는 화면 가장자리에만 둔다. 가운데는 게임을 위해 비운다.
- 상태는 숫자보다 막대, 색, 아이콘으로 먼저 보여 준다. 숫자는 보조로 작게.
- 한 화면에 강조색은 하나. 위험(피해, 과열)은 강조색과 다른 색을 쓴다.
- 글자 크기는 값 문서의 단계(작게, 본문, 제목)만 쓴다. 중간 크기를 새로 만들지 않는다.
- 결과 화면과 메뉴의 배경 막은 팔레트의 가장 어두운 색을 60~80% 불투명도로 쓴다(순수한 검정 금지).
- 처음 보는 사람이 3초 안에 무엇이 체력이고 무엇이 누를 것인지 알아야 한다.
