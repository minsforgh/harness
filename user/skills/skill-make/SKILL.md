# skill-make

상태: 시험 중. 쓸 때마다 아래 "시험 기록"에 한 줄 남긴다.

스킬을 만드는 방식은 이 스킬이 정하고, 평가 도구는 skill-creator(claude.ai 동기화 스킬, `anthropic-skills:skill-creator`)를 빌려 쓴다. skill-creator는 계정 동기화로 갱신되므로 복사하거나 고치지 않는다. skill-creator를 그대로 따르면 끝까지 한 번에 진행하는데, 사용자는 단계마다 보고 정하기를 원한다. 그래서 이 스킬이 언제 제안하고 어디서 멈출지를 정한다.

## 순서

0. dev-wiki 세션에서 한다. 프로젝트 세션이면 만들 스킬과 이유를 보고만 하고 멈춘다(프로젝트에서 하네스 원본을 고치지 않는다).
1. 겹치는 것을 찾는다: dev-wiki `_harness/`의 묶음과 `trial/`, 설치된 플러그인 스킬(공식 Unity, Orca 스킬 포함), claude.ai 동기화 스킬. 겹치면 새로 만들지 않고 기존 것을 고치거나, 그 스킬을 부르는 작은 스킬로 만든다(grilling 개인 복사본, 이 스킬처럼).
2. 정할 것이 여럿이면(경계, 위치, 값 파일 형식) 바로 쓰지 않고 "grilling으로 따져 볼까요?"를 한 줄로 제안한다.
3. 쓴다(아래 "형식").
4. 놓는다: 효과가 입증되지 않은 새 스킬은 `_harness/trial/<이름>/`에 두고, 쓰기 전에 통과 기준(제때 불렸나, 단계를 따랐나, 무엇을 잡았거나 줄였나, 비용)을 그 폴더 README에 먼저 적는다. 입증된 것만 묶음(`_harness/user/skills/` 또는 `_harness/packs/<묶음>/skills/`)에 넣는다. 고치는 중 시험은 `claude --plugin-dir <dev-wiki>/_harness/<묶음 폴더>`, 반영은 `node <dev-wiki>/_harness/release.mjs <플러그인 이름>`. junction은 쓰지 않는다.
5. 평가를 한 줄로 제안한다: "skill-creator로 스킬을 쓴 결과와 안 쓴 결과를 비교해 볼까요?" 스스로 돌리지 않는다. 거절하면 같은 스킬에서 다시 제안하지 않는다. 고친 정도가 작으면(문구, 경로) 제안하지 않는다.
6. 수락하면 skill-creator를 불러 아래 "평가 단계"대로 한다.

## 형식

- 폴더: `<묶음 폴더>/skills/<이름>/SKILL.md`(또는 `trial/<이름>/SKILL.md`), 필요하면 `templates/`, 목록 파일. 이름은 영문 kebab-case. 플러그인 안에서는 `<플러그인>:<이름>`으로 불린다.
- frontmatter: `name`, `description`(한국어, 무엇을 하는지와 언제 쓰는지, 쓰지 않는 경우). 사용자가 말할 법한 문구를 따옴표로 넣는다.
- 본문은 한국어. 첫 줄 아래 `상태: 시험 중`, 끝에 "시험 기록" 표(날짜, 프로젝트, 무엇을 했나, 잘 된 것과 고칠 것).
- 규칙은 개인 스킬에, 프로젝트마다 다른 값은 프로젝트 문서에 둔다. 스킬은 값의 위치만 안다.
- 왜 그렇게 하는지 한 문장씩 적는다. 대문자 MUST 같은 강조 대신 이유로 설득한다.

## 평가 단계

각 단계 끝에서 멈추고 사용자의 답을 기다린다.

1. 시험 문제: 실제로 할 법한 요청 2~3개와 각각 무엇을 보는지를 표로 보여 준다. 스킬이 사용자에게 물어야 하는 상황(값이 비어 있음)은 시험 문제로 하나 넣으면 차이가 잘 드러난다.
2. 사람이 정할 기준은 에이전트가 만들지 않는다. 말투 예시, 취향, 합격선처럼 스킬이 "사람에게서 받는다"고 정한 값이 시험에 필요하면, 후보 방향을 보여 주고 사용자가 고르거나 쓴다. 에이전트가 만든 예시로 시험하면 에이전트 말투를 정답으로 삼게 된다.
3. 실행: 확인받은 뒤 스킬을 쓴 실행과 안 쓴 실행을 함께 띄운다. 서브에이전트는 결과를 글이나 파일로 작업 폴더에만 남기고, 프로젝트와 dev-wiki 파일을 고치지 않게 지시한다.
4. 결과: skill-creator의 뷰어(`eval-viewer/generate_review.py`)를 띄우고, 눈에 띈 차이를 세 줄 안으로 말한다. 사용자가 보고 의견을 남길 때까지 고치지 않는다.
5. 고칠 점: 의견을 바탕으로 고칠 곳을 짧게 보여 주고 승인받은 뒤 고친다. 다시 돌릴지는 사용자가 정한다.
6. description 다듬기(skill-creator의 Description Optimization)는 스킬이 안정된 뒤 따로 제안한다.

작업 폴더(`<이름>-workspace/`)는 dev-wiki 밖, 세션 임시 폴더에 둔다(위키 커밋에 결과물이 섞이지 않게). 시험 문제 폴더(`evals/<문제 이름>/`)는 스킬 폴더에 남겨 다음에 다시 쓴다.
