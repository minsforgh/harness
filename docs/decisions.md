## 원칙 1. 효과는 도구에서 나왔고, 문장 규칙은 지켜지지 않았다

**상황**: 하네스 이전 방식(AGENTS.md에 작업 흐름과 마감 절차를 문장으로 적음)으로 Unity POC 하나를 끝냈다.

**근거**: 그 프로젝트 기록에서 실제로 문제를 잡은 것은 커밋 전 코드 검사 1건, 확인 단계 약 6건, 사람의 플레이테스트였다. 에이전트는 보고에 확인과 마감 단계를 약 30번 적었지만 실제 호출은 1번(준비만)과 0번이었다.

**결정**: 강제할 것은 훅과 커밋 전 검사로 옮기고, 판단이 필요한 것만 짧은 규칙으로 남긴다. 함께 정한 원칙: 금지보다 맞는 길을 가장 싼 길로(필요한 도구를 처음부터 깔아 둔다), 엔진 사용법은 공식을 따르고 차이만 가진다, 항상 읽히는 글은 짧게, 평가는 자기 보고가 아니라 기록으로, 검증 전에는 묶음에 넣지 않는다.

## Q3. 훅 우선, 지켜지지 않는 규칙은 지운다

강제할 수 없고 실제로 지켜지지 않은 규칙은 남겨 두면 읽히는 글만 늘린다. 훅으로 옮길 수 있으면 옮기고, 아니면 지운다.

## Q6. 보고는 증거 세 항목으로

"보고 첫 줄에 확인 방식을 적는다"는 규칙은 보고에만 적히고 실제 확인으로 이어지지 않았다. 그래서 지우고, 보고에는 **확인한 값, 사람이 직접 볼 것, 확인하지 못한 것** 세 가지만 쓰게 했다. 훅은 두지 않았다(형식은 강제해도 내용의 참을 강제할 수 없다).

## Q31. 프로젝트 세션은 하네스 원본을 고치지 않는다

**근거**: 이전 프로젝트 세션들이 원본을 약 90번(이후 기준 정정으로 73번) 고쳤고, 일부는 그 프로젝트 사정에 맞춘 수정이었다.

**결정**: 프로젝트 세션은 문제와 근거를 보고만 하고, 고치는 일은 원본 저장소 세션에서 한다. PreToolUse 훅(`user/hooks/guard_source.py`)이 원본을 고치려 하면 사용자에게 묻는다.

## Q46. 규칙은 프로젝트에 복사하지 않고 플러그인이 주입한다

처음 설계는 묶음마다 AGENTS.md에 표식 블록을 복사하는 것이었다. 그러면 원본을 고칠 때마다 모든 프로젝트를 다시 적용해야 하고, 프로젝트마다 다른 시점의 규칙이 남는다. 그래서 묶음의 `rules.md`를 SessionStart 훅이 주입하게 바꿨다. 원본을 release하면 켠 프로젝트가 모두 같이 바뀐다.

## Q57. 실제로 막은 일이 0번인 검사는 뺀다

커밋 금지 파일 검사(`forbidden.txt`)를 기록에서 세어 보니 실제로 막은 일이 0번이었고, 기본 항목은 이미 `.git/info/exclude`에 있었으며 새 구조는 그 파일을 만들지도 않았다. 검사를 뺐다. 필요해지면 그때 다시 정한다.

## Q93. 쓰임이 늘 같이 붙어 다니는 묶음은 합친다

game 묶음(구조 검사, 씬 조립 뼈대)을 따로 두려 했지만, 그 부품이 모두 Unity C# 코드이고 프로필에서 unity와 game이 늘 같이 켜졌다. unity 묶음에 합쳤다. 게임이 아닌 Unity 프로젝트나 Unity가 아닌 게임이 생기면 그때 나눈다.

## Q119. 평가는 비율과 사람의 판정만 비교한다

- 비교 표에는 비율, 도구 시간당 수, 사람의 판정만 올린다. 자동으로 뽑은 후보 수는 올리지 않는다
- 지표마다 어느 쪽이 좋은지와 짝 지표를 미리 적어 둔다(결과를 본 뒤 해석을 고르지 않게)
- 기준선이 POC 마감 국면이므로 같은 국면끼리 비교하고, 한 번의 비교로 효과라고 말하지 않는다
- 같은 프로젝트에서 하네스를 껐다 켰다 하는 비교는 혼자 쓰는 환경에서 비용이 커 하지 않는다

## Q156, Q167. 팀 저장소: 팀원에게 닿는 것은 저장소 파일로

**문제**: 팀원은 내 플러그인을 깔지 않는다. 그런데 컨벤션, 커밋과 PR 형식, 문서 규칙은 팀원 결과물에도 적용돼야 한다.

**결정**: 층을 나눈다.
- 팀원 결과물에 영향을 주는 것 -> 저장소 층: AGENTS.md 표식 블록, `.githooks/`(main 직접 push 막기, 플러그인 없이 도는 문서 검사 사본), PR 템플릿, `docs/SETUP.md`
- 내 작업 방식(계획 먼저, 질문 라운드 제안 등) -> 개인 층: 내 PC에만 local 범위로 켠 플러그인
- 프로필 `unity-team` = core + unity + team. 저장소 `.claude/settings.json`에는 내 플러그인을 넣지 않는다

## Q172. main을 잠글 수 없으면 사후에 잡는다

**상황**: 팀원 대부분이 Codex를 쓰고, 무료 플랜 비공개 저장소라 main 보호 규칙을 걸 수 없다. 이전 팀 프로젝트에서는 초반에 같은 이름의 폴더를 각자 만들어 충돌이 잦았다.

**근거**: 이전 팀 저장소의 merge 86개 중 16개가 충돌했고, 폴더 `.meta` 충돌 11건 중 10건이 첫날이었다. PR 없이 main에 들어온 커밋도 여섯 번 있었다(모두 pre-push 훅을 넣기 전).

**결정**:
- Codex: AGENTS.md와 git 훅은 Codex에도 그대로 닿는다. 프로젝트 `.codex/` 설정은 신뢰한 폴더에서만 읽으므로 SETUP에 "폴더 신뢰" 줄을 더했다
- main 잠금 대신: 팀 규칙에 "커밋 전에 훅 경로가 연결됐는지 본다", PR 검사 스크립트에 "PR 없이 main에 들어온 커밋" 찾기를 더했다
- 폴더 배치: 종류별(`Assets/Scripts/<시스템>`)이 아니라 시스템마다 `Assets/<시스템>/` 하나. 충돌이 폴더 `.meta`뿐이면 main 쪽을 고른다

## Q174. 지식 환류는 제안만, 빈칸이 만든 실수는 검사로 막는다

**환류**: 프로젝트에서 다음에도 쓸 지식이 나오면 에이전트가 보고 끝에 `wiki 후보: <한 줄>`을 붙이고, Stop 훅이 PC의 대기열(git 밖)에 모은다. 반영은 사람이 고른 것만 한다. 팀 저장소에 흔적이 남지 않는다.

**런타임 화면 조립**: 첫 하네스 프로젝트에서 게임 요소를 실행 중 코드로 만들어 씬에서 아무것도 보이지 않았다. 원인은 규칙 위반이 아니라 빈칸이었다(배치 규칙이 없었고, POC의 "임시 그림" 방침이 가장 짧은 길로 밀었고, 에이전트에게는 prefab 만들기가 코드보다 훨씬 비싸다).
- 규칙: 사람이 보고 고칠 게임 요소는 prefab과 씬으로
- 커밋 전 검사(`packs/unity/git/checks/runtime_build.py`): 이번 커밋에 새로 더한 런타임 C# 줄에서 `new GameObject`, `AddComponent` 등을 막는다. `// harness:runtime-ok: 이유`가 있으면 통과
- 팀 저장소에도 검사 사본을 넣어 플러그인 없는 팀원 커밋에도 돈다

## Q178. 배포는 시험 통과 지문이 있을 때만

시험 한 번이 2분 넘게 걸려 release마다 직접 돌리면 묶음 넷에 8분이 넘는다. 그래서 `tests/run.mjs`가 모두 통과하면 플러그인 원본의 지문을 `tests/.passed`에 남기고, `release.mjs`는 지금 원본이 그 지문과 다르면 멈춘다(`--untested`는 급할 때만). 같은 결정에서 "훅 하나가 넣는 글은 9,000자 아래"를 시험으로 고정했다.

## Q179. 파일 통째 다시 쓰기를 규칙과 지표로

**근거**: 원본 저장소 세션 하나가 압축 20번. 고정 부하(도구 정의, 스킬 목록 등 약 27만 자)보다 작업 출력이 컸다. 기록 전체를 세어 보니 Edit 831번(35.5만 자) 대 통째 다시 쓰기 52번(22.2만 자): 횟수로는 6%인데 쓴 글자로는 38%였다.

**결정**: core 규칙에 "있는 파일은 바뀐 부분만 고친다. 통째 다시 쓰기는 새 파일이거나 대부분을 바꿀 때뿐"(Claude와 Codex 도구 이름을 둘 다 적음). 평가에 `tools.file_edits` 지표(통째 비율, 파일별 횟수)를 더했다.

## Q182. 첫 프로젝트 기록 분석으로 규칙 셋을 더함

**근거**: 하네스로 만든 첫 POC를 평가 스크립트로 세어 보니 기준선보다 나빠진 비율은 없었다. 사용자 메시지 171개를 분류하니 사람이 가장 많이 고친 것은 게임 안 문구(15번 넘게)와 UI 겹침, 가림, 잘림(10번 안팎, "끝났다"고 한 뒤 나온 지적 12건의 대부분)이었다. 한 세션이 27시간, 압축 17번이었다.

**결정**:
- poc 규칙에 문구 한 줄(한 문장 한 가지, 아는 것과 보이는 숫자는 다시 쓰지 않기, 틀린 단순화 금지). POC에서만 에이전트가 쓰고 본 개발에서는 사람이 쓴다
- unity 규칙: UI를 바꾸면 가장 긴 문구와 가장 많은 표시로 캡처해 겹침을 본다. Player 빌드는 요청이 있거나 Player에서만 깨질 변경일 때만(빌드가 설정 파일을 다시 쓴다)
- core 규칙: 마일스톤이 끝났거나 압축이 세 번 넘으면 새 세션을 제안한다
- 팀 AGENTS.md 블록에는 새 세션 줄과 빌드 줄을 넣지 않았다. 넣으면 크기 한도(20 KiB)에 13바이트만 남았다
